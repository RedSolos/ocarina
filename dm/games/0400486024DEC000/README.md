# The Legend of Zelda: Ocarina of Time (`0400486024DEC000`)

A Switch 2 game: update v131072, SDK 22.2.8 (`Ounce`). Nintendo EPD's engine (sead, agl, gsys, Havok, CRIWARE; project `Owl`, with Tears of the Kingdom's file layout) on NVN2. Modules `main`, `subsdk0` (NintendoSDK_movie) and `sdk`. Update v131072 has an optional host render-scale ceiling. Status: plays on the Mac through the title, the opening, a new file's first scene, Link's house and Kokiri Forest, with saves, at about 59 fps with the picture close to console video. Mac only so far.

## Render-scale ceiling

Update v131072 (`main` build `e0f3ccfaf50065ae4ea01eb5aeb13b1a`) accepts `DM_RENDER_SCALE=0.5` through `1.0`. The default `1.0` keeps the game's original scale. Lower values cap the scale the engine has selected, so dynamic resolution can still reduce it further. The output size and the game's upscaler follow their existing paths. For example, a host ceiling of `0.5` keeps a game-selected `0.4` and caps a game-selected `0.75` to `0.5`.

The rewriter checks the instruction at `main+0x31d3f48` before replacing its final scale store. The stub reads the existing host state page at `+0x10`, preserves the store's registers and condition flags, and advertises `RENDER_SCALE` so the launcher offers its existing Render scale control. Other builds receive no fixed-address hook. This is a deliberate game rendering option whose scale calculation lives in the game binary. It uses the existing shader libraries.

Validation on the M1 Pro exercised the original cap at 50% on the house-to-Kokiri Forest route. The isolated stub additionally preserves the source SIMD register, checked by ARM64 execution across caps, game-selected scales and condition flags. The test also checks the launcher setting against rewritten metadata. Sustained frame-rate gains, later areas and iOS remain unmeasured for this isolated change.

## Native output

- The launcher's **Output** (`DM_OUTPUT`, v131072): the game draws its picture into 80 % of the output (`nvnWindowSetCrop`, 2048x1152 of the docked 2560x1440) and the system scales it up, the console's own frame. The 80 % is two multiplies in the game's code (`main+0x6505c4`, `+0x6505d4`; not in `ModelSceneExtensionParam`), and with **Native** stubs there skip them: the crop, the 3D and its depth are the full output size and nothing is scaled. Framing and field of view stay the same.
- Measured (M5 Max, macOS 26.6.2, 2026-11-09, Castle Town market, Link standing, headless, the 300 frames after the scene settled, n=1 each; at 3024x1702 with the 3D's levels at x1.0, both from our own build): the 80 % frame, 3D 2419x1361: frame p50 / p95 16.67 / 17.64 ms, GPU p50 / p95 13.36 / 14.20 ms; native, 3D 3024x1702: 19.47 / 21.29 ms, GPU 17.34 / 18.37 ms, and the market no longer held 60 at that size. So 1.56 times the pixels cost 1.1 to 1.3 times the GPU; macOS sets the GPU clock per run. The pause menu, speech bubbles and button prompts draw at the full size.

## Dynamic resolution

- The controller (v131072; found by fingerprint, so the addresses are only for reading): the parameters are `game__gfx__DynamicResolutionParam` (`LoadThreshold`, `ReduceCounterMax`, `IncreaseCounterMax`, and a list of levels, each a `ResolutionReduceScale` and a `Priority`). Once a frame the update (`main+0x805aa0`) reads the frame's GPU time, subtracts what its cost model predicts at the current size and keeps the trend of that residual. The level function (`main+0x8065e0`) adds the residual to the model's cost at each level and returns the best level under the threshold: 0, the full 1536x864, when the current size fits. The update moves down after `ReduceCounterMax` frames that ask for it and back up after `IncreaseCounterMax`. Scripted `GPULoad` hints from event data (`main+0x31c3de0`) and `OneshotSetDynamicResolutionLoadThreshold` adjust it in cutscenes.
- Resolved on the host: after a loading screen it sat at its floor, 683x384, for minutes while the frame held 60 fps with GPU time to spare. A stale frame-start timestamp and event waits that idled the GPU made its timer read more than the frame took: [Dynamic resolution at its floor while the GPU has time to spare](../../../docs/reference/frame-rate.md#dynamic-resolution-at-its-floor-while-the-gpu-has-time-to-spare).
- Resolved in the game's model: with the host's timer right it still sat at 683x384 for good. The update takes the frame's load (about 0.2 ms a unit) less its small fixed-cost model, divides the rest by the square of the current scale, and the level function multiplies that back by each level's scale squared. The whole remaining cost is taken to grow with the pixel count, as on the Switch 2 its constants were tuned for. Here it hardly does: 683x384 cost 14.3 ms and 1536x864 14.7 ms on an M4 Pro (mesh, compute and the upscaler's fixed 2048x1152 dominate). A probe of the controller in play (levels 0..9 at 0.75..0.333 of 2048x1152, threshold 83, about 16.4 ms) read a load of 70-80 at 683x384, under the threshold. The extrapolation still put full size at 300-400, so it never stepped up.
- Current: the launcher's **Dynamic resolution** (`DM_DYNAMIC_RESOLUTION`; off by default upstream, on in this branch since 2026-11-10, from the profile's `dynamic_resolution on`). Off holds full resolution. On climbs one level at a time on the load measured at each level, with no model of how the cost grows, within the game's own level list, threshold and counters:
  - down when the load has been over the threshold for 8 frames in a row, and that level is marked as not fitting;
  - up when the load fits and the level above was never measured, fitted when last measured, or was measured more than about 10 s ago.

  Nothing is decided until a level has held 8 frames, since the load is read a few frames late. The 8 frames in a row keep a single slow frame, or the first frames at a new size, from rejecting a level that fits. An earlier version stepped down on 2 frames over and stopped at level 2 after one burst to 90 at level 1. A version that stepped up only when the load, scaled by the next level's pixel ratio, stayed under the threshold sat at the floor too: 70 × 1.3 is over 83. Result (M4 Pro, 2026-11-09, `kokiri-still`, the full library on chain a02f1e0dfdde): from the floor to full size, then mostly at 1536x864. The load there is about 83, the game's own threshold, so a sustained frame over moves it to level 1 (0.70) for about 10 s. 59.9 fps, all 1,800 frames held at one vsync, frame p99 16.89 ms, GPU p50 14.5 ms. Loads by level: 72 at the floor, 75 at level 6, 80 at level 2, 82 at level 1, 83 at full size.
- Current: the launcher's **Render scale** (`DM_RENDER_SCALE`, 0.5 to 1.0, 1.0 by default) fixes the 3D views at that fraction of the game's own size and holds the dynamic resolution at its top level, as on Breath of the Wild and Tears of the Kingdom: 0.75 draws the main passes at 1171x659, 0.5 at 781x439 (the engine's own rounding), the game's own upscaler to the output. Two stubs in the view-size update (found by its fingerprint) multiply the scale the game computes and make the frame recompute the sizes once; the level stub returns level 0 under a scale ([`patches.py`](patches.py), render scale). Measured on the M4 Pro (20-core GPU, 2026-11-09, `kokiri-deck`, docked, two runs each, main d8b2b64a1):

  | Render scale | main pass | GPU p50 / p95 | fps | frames over budget |
  |---|---|---|---|---|
  | 1.0 (the game's) | 1536x864 | 15.77 / 16.94 ms | 46 | 588 |
  | 0.75 | 1171x659 | 14.31 / 15.19 ms | 59.6 | 19 |
  | 0.5 | 781x439 | 13.25 / 14.34 ms | 59.7 | 18 |

  At the game's own size the GPU's p95 sits just over a vsync on this Mac, so the frame step holds 2 vsyncs for stretches of the route; at 0.75 it holds 60 fps. The pictures stay clean at both scales.
- Open: in heavier scenes it goes down to the floor for nothing. In the player's session (M4 Pro, 2026-11-09, Metal HUD) it held full size at loads of 80-84 until a scene took it to 94-102. It then stepped down to 683x384, where the load was still 83-86, about the same as at full size. It stayed near the floor at about 80 until a lighter scene (55 at the floor) let it climb again. ## Local city pipeline lookup validation

[Repeated archive misses while hybrid pipeline demand is saturated](../../../docs/reference/frame-rate.md#repeated-archive-misses-while-hybrid-pipeline-demand-is-saturated) was found on Apple M5 / macOS 27.0.1, game v131072, SDK 22.2.8. These gameplay measurements used baseline `bd979ced3ae6` and a host carrying local frame-step and packaging changes; the candidate added only the miss cache. They are historical evidence for the mechanism, not a fresh performance comparison on current main. In the city, frame 4500's 300-frame window had frame-time p50/p95/max 107.06/169.34/268.74 ms, GPU p50/p95 24.27/31.89 ms, and CPU translation 113.837 ms per frame. Its 9,208 failed archive searches cost 30,532.8 ms; the demand queue held 384 entries. A live sample spent 287/456 presentation-thread samples under Metal archive lookup.

After the process-local miss cache was installed, the player returned to the same area and reported roughly stable 30 fps. The new frame 3600 window measured frame-time p50/p95/max 28.49/33.78/37.54 ms, GPU p50/p95 27.85/33.33 ms, and CPU translation 6.439 ms per frame. Five failed archive searches cost 14.6 ms over those 300 frames. Earlier new-run windows had similar CPU costs (6.317–6.358 ms). GPU time now dominates those windows.

This is a same-area gameplay comparison, not a deterministic replay: camera, route and cache warmth were not held identical. Only this game was available locally; the regression harness could not locate its manually assembled build layout. The focused archive regression is rerun on the PR base; no new gameplay result is implied.
